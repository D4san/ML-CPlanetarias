# Evidencia B01 · Modelo de contenido y validadores

## Identificación

- Tarea: B01 · Implementar el modelo de contenido y sus validadores.
- Dependencias aceptadas: A02 y A03.
- Base: ADR-0002, esquemas públicos existentes, `src/content.config.ts` y validator vigente.
- Responsable y revisor: Codex integrador.
- Estado propuesto: aceptada.

## Entregas

- `src/lib/course-content.ts`: tipos y validador runtime para curso, sesión, bibliografía,
  estación, unidad, ejemplo, concepto, referencia, asset, procedencia, derechos y estado
  editorial.
- `src/lib/course-content.test.ts`: pruebas positivas y negativas con diagnósticos por ID/campo.
- `tests/fixtures/course/`: fixtures válidos de S01, S00 sin rutas, y fixtures inválidos de
  ejemplo ausente y procedencia absoluta. Permanecen fuera de `docs/content/` y del build.
- `scripts/validate-content.mjs`: comprobación de fixtures de curso integrada al comando
  existente, además de la validación de inbox/outbox/colecciones públicas.
- `schemas/public-content.schema.json` y `src/content.config.ts`: soporte coherente para
  procedencia Obsidian heredada y procedencia `repo` con `source_path` relativo, manteniendo
  revisión, visibilidad, `publish_ready` y derechos como condiciones independientes.
- `src/layouts/ArticleLayout.astro`: adaptación mínima del consumidor para mostrar una ruta de
  procedencia de repositorio cuando no existe `source_note` de Obsidian.

## Criterios de aceptación

- B01-AC1: cumplido. Los fixtures válidos S01/S00 pasan el validador runtime y la comprobación
  integrada; los inválidos fallan con campo/ID responsable. El esquema público mantiene la
  distinción de procedencia.
- B01-AC2: cumplido. Las referencias se resuelven por ID y las reglas no dependen del orden de
  lectura; las rutas relativas y estados editoriales se validan explícitamente.
- B01-AC3: cumplido. Cada sesión exige bibliografía con material y cada unidad exige al menos
  un ejemplo con fuente existente y no vacía; no se aceptan enlaces ficticios vacíos.
- B01-AC4: cumplido. Los paquetes de `inbox/` conservaron su estado real y los fixtures no se
  cargan en ninguna colección Astro.

## Comprobaciones

| Comando | Código | Resultado |
| --- | ---: | --- |
| `npx.cmd prettier --write` sobre entregas B01 | 0 | Archivos formateados. |
| `npm.cmd run check:astro` | 0 | 56 archivos, 0 errores, 0 warnings, 0 hints; colecciones públicas vacías. |
| `npx.cmd vitest run src/lib/course-content.test.ts` | 0 | 1 archivo, 4 tests pasan. |
| `npm.cmd run test:unit` fuera del sandbox autorizado | 0 | 11 archivos, 56 tests pasan. |
| `node scripts/validate-content.mjs` | 0 | Paquetes/outbox válidos y 4 fixtures evaluados; los dos fixtures `invalid-*` fallan las reglas esperadas. |

El primer intento sandbox de Vitest conserva el bloqueo conocido `spawn EPERM`; la ejecución
autorizada fuera del sandbox es la evidencia utilizada. No se ejecutaron builds ni Playwright en
paralelo, y no se añadió ningún import/glob de `inbox/` al build.

## Limitaciones

El validador runtime comprueba que `source_path` sea portable, pero la existencia física de cada
ruta de procedencia se verifica en el contexto de la tarea que la usa. El contenido público sigue
vacío y ningún fixture se promocionó. B03–B04 deben integrar el contrato común en la configuración
del fork y la generación de páginas.
