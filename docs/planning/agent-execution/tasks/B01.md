src/lib/course-content.ts y pruebas (nuevos); schemas/public-content.schema.json; src/content.config.ts; scripts/validate-content.mjs; fixtures bajo tests/fixtures/course/; protocolos de procedencia/ciclo solo si A03 requiere sincronizarlos.

Las rutas son relativas a la raíz del repositorio. Los nombres nuevos son destinos propuestos que A02 fija antes de implementarlos. Pedir al integrador una reasignación si aparece una necesidad fuera de esta lista; continuar con lo independiente.

## Lista de tareas

- [ ] Implementar los tipos y la validación de curso/sesión/estación/unidad y referencias del contrato. Usar los validadores existentes; mantener equivalentes JSON Schema y esquema Astro, sin crear dos definiciones incompatibles.
- [ ] Implementar la compatibilidad editorial acordada: las entradas antiguas de Obsidian siguen siendo válidas; el origen repo exige una ruta relativa real. Mantener status, visibility, publish_ready y derechos como condiciones independientes.
- [ ] Crear fixtures mínimos de S01, S00 sin rutas y conceptos/ejemplos; permanecerán fuera de las colecciones públicas. Crear casos inválidos por duplicados, referencias ausentes, orden ambiguo, origen inválido y derechos incompletos.
- [ ] Validar que cada unidad explicativa enlaza al menos un ejemplo y que cada sesión tiene bibliografía inicial; permitir estados editoriales pendientes en preparación, rechazarlos al promover a contenido público.
- [ ] Conectar la validación con el comando existente y documentar mensajes con archivo/ID/campo. Comprobar que no se introduce ningún import ni glob de inbox en build.

## Criterios de aceptación

- [ ] B01-AC1: Los fixtures válidos pasan ambos esquemas pertinentes y los inválidos fallan con el campo o ID responsable.
- [ ] B01-AC2: Las referencias y las reglas científicas/editoriales se validan sin depender del orden de lectura de archivos.
- [ ] B01-AC3: La bibliografía y el ejemplo requerido no se satisfacen con cadenas vacías, enlaces ficticios ni arrays vacíos.
- [ ] B01-AC4: Los paquetes existentes mantienen su estado real y los tests no publican fixtures.

## Evidencia y validación

Pruebas de validadores, npm run check y builds raíz/subruta; matriz de compatibilidad con entradas actuales.

Aplicar los gates proporcionales de VALIDATION.md. Completar [el informe de entrega](../templates/DELIVERY.md); marcar un criterio solo con evidencia. El agente propone entrega; el revisor acepta la tarea en BOARD.md.

## Criterio de logro

Un agente de contenido puede construir una sesión válida con ejemplos sin editar el motor ni adivinar requisitos.

## Límites de esta tarea

No migrar aquí todas las escenas ni poblar colecciones con contenido sin revisión.
